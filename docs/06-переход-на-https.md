# Переход на HTTPS

Код к этому готов: переключаются два флага в конфиге, править ничего не нужно.
Здесь — порядок действий и грабли, на которые легко наступить.

## Почему это важно именно для вашего портала

По HTTP в сети передаётся открытым текстом всё: пароли из формы входа,
содержимое документов, переписка и cookie сессии. Кто угодно, имеющий доступ
к сетевому оборудованию или к порту коммутатора, может это читать —
а перехваченной cookie достаточно, чтобы работать в портале от чужого имени
без всякого пароля.

Пока функционала мало, риск невелик. С появлением файлового хранилища
(этап 3) и переписки (этап 5) он становится реальным.

## Шаг 1. Получить сертификат

Домен внутренний, публичные центры сертификации на `ftp.domen.pro`
сертификат не выдадут. Варианты:

**Вариант А — служба сертификации Active Directory (рекомендуется).**
Если в домене развёрнута роль AD CS, сертификат выпускается за пять минут,
а доверие к нему у доменных компьютеров уже есть — корневой сертификат
раздаётся групповыми политиками автоматически. Ничего настраивать на
клиентах не придётся.

**Вариант Б — самоподписанный сертификат.**
Делается одной командой, но корневой сертификат придётся раздать
на все компьютеры групповой политикой. Иначе браузеры будут показывать
предупреждение, а пользователи привыкнут его игнорировать — что само по себе
плохая привычка.

```powershell
# Вариант Б, если AD CS нет.
# Оба имени перечислены намеренно — см. пояснение ниже.
New-SelfSignedCertificate -DnsName "ftp.domen.pro", "ftp" `
    -CertStoreLocation "cert:\LocalMachine\My" `
    -FriendlyName "Portal ftp.domen.pro" `
    -NotAfter (Get-Date).AddYears(3)
```

Что бы вы ни выбрали, в сертификате обязательно должно быть поле
**Subject Alternative Name**, и в нём — **оба** имени: `ftp.domen.pro`
и короткое `ftp`. Современные браузеры поле Common Name больше не смотрят,
а имя, которого нет в SAN, считают несовпадением: пользователь, набравший
`https://ftp/`, получит предупреждение о недоверенном сертификате.

Если сертификат выпускается через AD CS, укажите оба имени в запросе
(в шаблоне — «Alternative name», тип DNS, две записи).

Проверить, что попало в готовый сертификат:

```powershell
(Get-ChildItem cert:\LocalMachine\My | Where-Object Subject -like "*ftp.domen.pro*").DnsNameList
```

## Шаг 2. Привязать сертификат к сайту в IIS

```powershell
Import-Module WebAdministration

# отпечаток нужного сертификата
Get-ChildItem cert:\LocalMachine\My | Where-Object Subject -like "*ftp.domen.pro*"

$cert = Get-ChildItem cert:\LocalMachine\My | Where-Object Subject -like "*ftp.domen.pro*"

# Привязка для полного имени
New-WebBinding -Name "Portal" -Protocol https -Port 443 -HostHeader "ftp.domen.pro" -SslFlags 1
New-Item -Path "IIS:\SslBindings\!443!ftp.domen.pro" -Value $cert -SSLFlags 1

# И для короткого — так же, как на порту 80
New-WebBinding -Name "Portal" -Protocol https -Port 443 -HostHeader "ftp" -SslFlags 1
New-Item -Path "IIS:\SslBindings\!443!ftp" -Value $cert -SSLFlags 1
```

`-SslFlags 1` включает SNI — без него IIS не даст привязать два имени
к порту 443 на одном адресе.

**Проверьте, что HTTPS работает, ДО того как что-то менять в приложении:**

```powershell
Invoke-WebRequest https://ftp.domen.pro/healthz -UseBasicParsing
Invoke-WebRequest https://ftp/healthz -UseBasicParsing
```

Оба запроса должны вернуть `ok` без ошибок сертификата. Если тут проблема —
решайте её сейчас. Дальше идти нельзя.

## Шаг 3. Включить редирект и Secure-cookie

Только теперь, в `C:\inetpub\portal\appsettings.json`:

```jsonc
"Security": {
  "RequireHttps": true,     // ← было false
  "UseHsts": false,         // ← пока оставить false
  ...
}
```

```powershell
Restart-WebAppPool -Name "PortalPool"
```

Что изменится:
- запросы по HTTP автоматически перенаправляются на HTTPS
- cookie `Portal.Auth` получает флаг `Secure` и по HTTP больше не отправляется

Проверьте:

- [ ] `http://ftp.domen.pro/` перенаправляет на `https://ftp.domen.pro/`
- [ ] Вход работает
- [ ] В инструментах разработчика (F12 → Application → Cookies)
      у `Portal.Auth` появился флаг `Secure`

> Если после этого войти не получается — почти наверняка HTTPS работает
> не до конца. Верните `RequireHttps: false`, перезапустите пул и вернитесь
> к шагу 2.

## Шаг 4. HSTS — в последнюю очередь и осторожно

HSTS — это заголовок, которым сайт говорит браузеру: «ко мне ходить только
по HTTPS». Браузер это **запоминает** и дальше сам отказывается открывать
сайт по HTTP.

Отсюда и опасность: если сертификат сломается или истечёт, пользователи
не смогут открыть портал вообще, а обойти запрет через кнопку «всё равно
продолжить» браузер не даст. Сбросить придётся вручную на каждом компьютере.

Поэтому:

1. Сначала поживите на `RequireHttps: true` хотя бы неделю
2. Затем включите HSTS с маленьким сроком:

```jsonc
"UseHsts": true,
"HstsMaxAgeDays": 1
```

3. Убедитесь, что всё в порядке, и только потом увеличивайте срок
   до 30, а затем до 365 дней

Не включайте HSTS, если сертификат самоподписанный и не роздан на все
компьютеры групповой политикой.

## Шаг 5. Заодно

Когда HTTPS заработает, можно ужесточить ещё две вещи.

**Имя cookie с префиксом `__Host-`.** Такой префикс браузер принимает только
по HTTPS и только для текущего домена без указания пути. Это дополнительная
защита от подмены cookie через поддомен. В `Program.cs`:

```csharp
options.Cookie.Name = "__Host-Portal.Auth";
```

Учтите: после переименования все текущие сессии оборвутся — пользователям
придётся войти заново. Делайте в нерабочее время.

**Не оставляйте открытым порт 80.** Редирект с HTTP на HTTPS должен работать,
но когда все привыкнут заходить по HTTPS, привязку на порт 80 разумно убрать
совсем.

## Напоминание про срок действия

Внутренние сертификаты имеют свойство истекать в самый неудачный момент.
Поставьте себе напоминание за месяц до даты в поле «Действителен по».

Посмотреть срок:

```powershell
Get-ChildItem cert:\LocalMachine\My |
    Where-Object Subject -like "*ftp.domen.pro*" |
    Select-Object Subject, NotAfter
```
