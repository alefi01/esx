# Архитектура: что выбрано и почему

Документ объясняет решения, принятые на этапе 1. Если через полгода возникнет
вопрос «а почему сделано так», ответ должен быть здесь.

## 1. Стек

| Что | Выбрано | Почему |
|---|---|---|
| Платформа | .NET 10 (LTS) | Поддержка Microsoft до ноября 2028. Родная для Windows Server и IIS. |
| Веб-фреймворк | ASP.NET Core **Razor Pages** | См. ниже. |
| Интерфейс | Обычный HTML + один файл CSS | В сети нет интернета: npm, CDN и сборщики фронтенда недоступны. |
| Аутентификация | LDAP к контроллеру домена + cookie | Требование задачи. |
| База данных | PostgreSQL + Entity Framework Core | Подключена на этапе 2. На этапе 1 хранить было нечего. |
| Файлы | На диске, не в БД | Проще бэкап, проще отдача, и это единственный вариант, совместимый с DFS-R. |

### Почему Razor Pages, а не MVC и не Blazor

**Razor Pages** — это «страница + файл с её кодом». Открыли `Login.cshtml` —
рядом лежит `Login.cshtml.cs` с обработчиками. Ничего искать не нужно.

**MVC** раскидывает то же самое по трём папкам (Controllers, Views, Models).
На большом проекте с командой это оправдано, на портале из десятка страниц —
лишняя навигация.

**Blazor Server** отпадает по конкретной причине: он держит между браузером и
сервером постоянное соединение WebSocket и гоняет по нему каждое нажатие.
У вас между офисами канал с урезанным MTU (~1400) и потерями крупных пакетов —
это худший сценарий для постоянного соединения. Разрывы будут выглядеть как
«портал завис». Обычные HTTP-запросы страниц переживают такой канал спокойно.

### Почему один проект, а не несколько

Стандартный «взрослый» подход — разложить решение на `Domain`,
`Application`, `Infrastructure`, `Web`. Здесь этого сознательно нет.

Такое разделение окупается, когда над кодом работает несколько человек или
когда одну и ту же логику используют несколько приложений. У вас ни того,
ни другого: один портал, один сопровождающий, двадцать пользователей.
Цена разделения — четыре проекта, ссылки между ними и вопрос «а в каком
проекте это лежит?» на каждое изменение.

Вместо этого один проект с говорящими папками:

```
Configuration/   классы настроек — один класс на секцию appsettings.json
Security/        имена политик и claim'ов (константы вместо строк по всему коду)
Services/        логика, не привязанная к страницам
Pages/           страницы
```

Если проект вырастет, разделить его позже несложно: границы уже проходят
по папкам.

## 2. Как устроен вход

```
Браузер                Портал                          Контроллер домена
   |                      |                                    |
   |-- POST логин/пароль ->|                                    |
   |                      |-- определяет офис по IP клиенту     |
   |                      |-- LDAP bind (проверка пароля) ----->|
   |                      |<-- ок / ошибка 49 -----------------|
   |                      |-- поиск пользователя и его групп -->|
   |                      |<-- displayName, mail, группы ------|
   |                      |-- проверяет членство в WebUsers     |
   |<-- Set-Cookie -------|                                    |
```

Ключевые решения:

**Пароль нигде не хранится.** Портал не имеет собственной базы паролей —
и не будет иметь. Проверку выполняет контроллер домена операцией bind.

**Сервисной учётной записи нет.** Список групп читается тем же соединением,
от имени только что вошедшего пользователя. Многие примеры в интернете
предлагают завести отдельную учётку с паролем в конфиге — это лишний секрет,
который придётся хранить, менять и защищать. Прав рядового пользователя домена
хватает, чтобы прочитать собственные группы.

**Режим проверки пароля — Negotiate (Kerberos/NTLM), а не simple bind.**
При simple bind пароль уходит на контроллер домена открытым текстом; без LDAPS
его видно снифером в локальной сети. Negotiate работает в домене «из коробки»,
сертификаты не нужны, пароль по сети не передаётся. Дополнительно включены
подпись и шифрование LDAP-трафика (`UseSigningAndSealing`).

Переключиться на simple bind можно (`AuthMode: "Basic"`), и у него есть одно
преимущество: AD возвращает точную причину отказа — истёк пароль, учётка
заблокирована и т.п. Но включать его допустимо только вместе с `UseSsl: true`.

**Вложенные группы раскрывает контроллер домена.** Запрос использует правило
`LDAP_MATCHING_RULE_IN_CHAIN` (OID `1.2.840.113556.1.4.1941`): один запрос
вместо рекурсивного обхода. Нюанс: «основная группа» (обычно `Domain Users`)
в результат не попадает — в AD она хранится отдельным атрибутом. Прав на портале
на `Domain Users` не выдаётся, так что это не мешает.

## 3. Роли — это буквально группы AD

Отдельной таблицы ролей нет. После входа каждая группа пользователя
кладётся в cookie как роль, поэтому в коде можно писать:

```csharp
User.IsInRole("WebUsers")
[Authorize(Roles = "Buhgalteriya")]
```

Управление доступом остаётся там, где вам привычно — в оснастке
«Active Directory — пользователи и компьютеры». Портал ничего про
пользователей не знает и списка их не ведёт.

**Обратная сторона, о которой надо знать.** Права снимаются с задержкой:
если убрать человека из группы, портал заметит это при следующем входе
или когда истечёт сессия (`Security:SessionHours`, по умолчанию 8 часов).
Мгновенный отзыв прав потребует перепроверки групп на каждом запросе —
это лишние обращения к AD. При необходимости добавим в событии
`OnValidatePrincipal` перепроверку раз в N минут.

**Второе.** Все группы едут в cookie на каждый запрос. При двадцати
пользователях и обычном числе групп это десятки байт. Если у кого-то
окажется несколько сотен групп, cookie распухнет — тогда в
`Login.cshtml.cs` надо будет оставлять только группы, интересные порталу.

## 4. Безопасность: что заложено сразу

| Механизм | Где | Зачем |
|---|---|---|
| Всё закрыто по умолчанию | `SetFallbackPolicy` в `Program.cs` | Новая страница закрыта автоматически; открывать надо осознанно. Забыть поставить защиту нельзя. |
| Antiforgery-токены | Razor Pages, автоматически | Чужой сайт не сможет отправить форму от имени вашего пользователя. |
| Выход только POST-ом | `Logout.cshtml.cs` | Иначе картинка `<img src=".../Logout">` на любом сайте выкидывала бы пользователей. |
| Защита от открытого редиректа | `Url.IsLocalUrl` в `Login.cshtml.cs` | `returnUrl` не может увести на чужой сайт. |
| Экранирование LDAP-фильтров | `LdapEscaper` | LDAP-инъекция — прямой аналог SQL-инъекции. |
| Отказ на пустой пароль | `LdapAdAuthenticationService` | LDAP на пустой пароль отвечает «успешно» (unauthenticated bind). Без явной проверки войти можно было бы вообще без пароля. |
| Одинаковый текст ошибки | `Login.cshtml.cs` | Иначе форма входа становится способом узнать, какие учётки есть в домене. |
| Счётчик неудачных попыток | `LoginThrottle` | Главное — не дать заблокировать доменные учётки перебором. |
| Ключи cookie на диске | `PersistKeysToFileSystem` | Иначе при перезапуске пула IIS все разом «разлогиниваются». |
| Заголовки безопасности | `Program.cs` | `nosniff`, `X-Frame-Options`, CSP. |
| Текст объявлений всегда экранируется | `PlainTextFormatter` | HTML от пользователя не принимается вовсе — закрыт целый класс уязвимостей (XSS). |
| Автор берётся из cookie, а не из формы | `Create.cshtml.cs` | Иначе объявление можно опубликовать от чужого имени. |
| Права на объявление проверяются дважды | `Edit`, `Delete` | При открытии формы и повторно при сохранении: POST можно отправить в обход страницы. |
| Пароль базы вне репозитория | `appsettings.Production.json` | Файл в `.gitignore`, права сужены до пула IIS и администраторов. |

### Про счётчик попыток — почему это важнее, чем кажется

Если в домене настроена политика блокировки учётных записей, то форма входа
без ограничений превращается в оружие: пять запросов подряд с чужого компьютера —
и сотрудник заблокирован в домене. Поэтому портал считает неудачи сам и
перестаёт обращаться к контроллеру домена **раньше**, чем сработает доменная
блокировка. Держите `Security:MaxFailedLoginAttempts` ниже порога в доменной
политике паролей.

Счётчик ведётся по паре «логин + IP-адрес», а не по одному логину: иначе
один забывчивый сотрудник заблокировал бы форму входа для всех остальных.

## 5. Офисы и межофисный канал

`Services/Offices/OfficeResolver` сопоставляет IP клиента с подсетями из
конфига и определяет офис. Это используется уже сейчас — чтобы аутентификация
шла через «свой» контроллер домена, а не через межофисный канал.

На этапе 6 тот же сервис будет выбирать, с какой реплики DFS-R отдавать файл.
Поэтому он появился сразу: переписывать потом ничего не придётся.

Дополнительно, с оглядкой на MTU ~1400:

- LDAP используется только поверх TCP; CLDAP (тот же LDAP поверх UDP) выключен —
  именно UDP страдает от урезанного MTU сильнее всего
- отключено следование за «отсылками» (referrals): иначе запрос к своему
  контроллеру мог бы незаметно уехать в другой офис
- таймаут 10 секунд, после чего пробуется следующий контроллер

## 6. Готовность к HTTPS

Сейчас портал работает по HTTP, и код это учитывает. Всё, что связано с
переходом, собрано в секции `Security` конфига:

```jsonc
"RequireHttps": false,   // редирект на HTTPS + флаг Secure на cookie
"UseHsts": false         // заголовок HSTS
```

Когда сертификат появится, переключаются два флага — код не меняется.
Подробности и порядок действий: [06-переход-на-https.md](06-переход-на-https.md).

## 7. Объявления (этап 2)

**Текст хранится как обычный текст, не как HTML.** Это главное решение
раздела. Визуальный редактор означал бы приём HTML от пользователя, а его
пришлось бы очищать по «белому списку» отдельной библиотекой — иначе любой
публикатор смог бы выполнить свой скрипт в браузере у всех сотрудников.
Вместо этого разметку формирует сам портал (`Services/Text/PlainTextFormatter`),
а пользовательский ввод всегда экранируется. Поддерживаются переносы строк
и автоматическое распознавание ссылок `http://` и `https://` — этого хватает
для объявлений, а класс уязвимостей закрыт целиком.

**Права разведены на два уровня.** Политика `PublishAnnouncements` (группа
`WebPublishers` или администраторы) отвечает на вопрос «может ли человек
писать вообще». Правило `AnnouncementPermissions.CanModify` отвечает
на вопрос «может ли он трогать вот это конкретное объявление»: своё — автор,
любое — администратор. Второй уровень проверяется и при открытии формы,
и повторно при сохранении: между этими моментами могло пройти время,
а POST-запрос можно отправить и в обход страницы.

**Форма привязана к отдельной модели, а не к сущности.** Если привязывать
форму прямо к `Announcement`, злоумышленник может дослать в запросе поля,
которых в форме нет, — например `AuthorUserName`, — и опубликовать объявление
от чужого имени. В `InputModel` есть ровно два поля, автор берётся из cookie.

**Схема базы применяется при запуске приложения.** Это избавляет от переноса
на сервер инструмента `dotnet-ef` со всеми его зависимостями (там Roslyn,
около 50 МБ). Допустимо, потому что веб-сервер один; при появлении второго
это надо будет выключить (`Database:ApplyMigrationsOnStartup`) и накатывать
изменения вручную.

**Недоступная база не роняет портал.** Вход работает через Active Directory
и от PostgreSQL не зависит, поэтому при остановленной базе портал
запускается, пускает людей внутрь, а раздел объявлений сообщает о проблеме.
Техническая подробность ошибки при этом показывается только администраторам:
в тексте исключений бывают имена серверов и учётных записей.

## 8. Интерфейс: почему без библиотек

Оформление — один файл `wwwroot/css/site.css`, поведение страниц —
один файл `wwwroot/js/app.js`. Ни Bootstrap, ни jQuery, ни сборщика.

Причина прежняя: в вашей сети нет интернета, значит нет ни npm, ни CDN,
а любую библиотеку пришлось бы переносить руками и потом обновлять.
Плюс оба файла можно прочитать целиком и понять, что там происходит.

Что при этом получилось сделать своими силами:

- **вид проводника**: плитки папок и файлов, выделение мышью и с клавиатуры,
  контекстное меню по правой кнопке, окна поверх страницы;
- **перетаскивание файлов** из проводника Windows прямо в окно браузера;
- **буфер обмена**: Ctrl+C / Ctrl+X / Ctrl+V как внутри портала (между папками),
  так и для файлов, скопированных в проводнике;
- **ход загрузки**: файлы уходят на сервер запросом XMLHttpRequest, поэтому
  видно проценты, а страница не перезагружается;
- **анимации**: полоса загрузки страницы, всплывающие сообщения, появление
  меню и окон. Всё уважает системную настройку «уменьшить движение»;
- **тёмная тема** — по системной настройке, без отдельного переключателя.

Значки нарисованы в `Pages/Shared/_Icons.cshtml` как набор SVG-символов
и подключаются на страницу один раз. Шрифты со значками и картинки с CDN
в вашей сети недоступны, а десяток отдельных файлов ради иконок — лишняя возня.

Политика безопасности страницы (CSP) запрещает встроенные скрипты, поэтому
данные передаются в код страницы через `data-`атрибуты, а не через
вставленный в разметку `<script>`. Это ограничение не мешает, а страхует:
чужой код на страницу не попадёт, даже если куда-то просочится.

### Подводные камни Razor в .NET 10

Две особенности, на которых легко потерять полдня. Обе проявляются
**только при сборке с нуля** — при обычной пересборке результат берётся
из кэша, и ошибки не видно.

1. **Тег `<text>` больше не работает** в блоках кода `.cshtml`.
   Вместо него используйте `<span>` или `@@:`.

2. **Теги `article`, `section`, `header`, `footer`, `figure` нельзя ставить
   самым внешним элементом внутри блока кода** (`@@if`, `@@foreach`).
   Внутри `<div>` они работают, вне блоков кода — тоже.

Коварство в том, что ошибка показывается совсем в другой строке и часто
в другом файле: разбор ломается, и дальше сыплются мнимые ошибки вида
«не найден тип time». Если сборка вдруг рассыпалась в файле, который вы
не трогали, — ищите эти два случая.

Отсюда же практическое правило: **перед выкладкой собирайте с чистой папкой**,
иначе накопленный кэш скроет проблему до самого неудачного момента:

```powershell
Remove-Item -Recurse -Force src\Portal.Web\obj, src\Portal.Web\bin
dotnet build
```

## 9. Зависимости

Внешних зависимостей семь, суммарно 5.5 МБ. Все `.nupkg` лежат в `packages/`,
сборка проходит без интернета.

```
System.DirectoryServices.Protocols 10.0.10       клиент LDAP
Microsoft.EntityFrameworkCore 10.0.10            работа с базой данных
  .Abstractions, .Analyzers, .Relational          (его же составные части)
Npgsql 10.0.3                                    драйвер PostgreSQL
Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3     связка EF Core и PostgreSQL
```

Всё остальное — часть .NET и ASP.NET Core. Пакетов для тестов в `packages/`
нет: они нужны только на машине разработки и занимают около 100 МБ.
