# Этап 3: файловое хранилище

Что появилось:

- дерево папок с правами доступа по группам Active Directory;
- наследование прав от родительской папки — с возможностью выключить;
- предел размера файла у каждой папки (по умолчанию 50 МБ);
- квота на суммарный объём папки;
- автоочистка папки по сроку хранения (по умолчанию выключена);
- корзина: удалённое лежит 30 дней и может быть восстановлено;
- запрет загрузки исполняемых файлов;
- журнал действий: кто что загрузил, скачал, удалил.

---

## Что нужно сделать на сервере

### Шаг 1. Отвести место под файлы

Папку с файлами держите **вне каталога приложения**. Иначе однажды
`dotnet publish` или чистка перед обновлением заденут документы.

```powershell
New-Item -ItemType Directory -Force -Path "D:\PortalFiles"

# Приложению нужно право читать, писать и удалять.
icacls "D:\PortalFiles" /grant "IIS AppPool\PortalPool:(OI)(CI)(M)"

# Обычным пользователям домена доступ к этой папке по сети НЕ нужен:
# все обращения идут через портал, который и проверяет права.
icacls "D:\PortalFiles" /inheritance:r
icacls "D:\PortalFiles" /grant "Администраторы:(OI)(CI)(F)" "SYSTEM:(OI)(CI)(F)" "IIS AppPool\PortalPool:(OI)(CI)(M)"
```

> Именно эту папку на этапе 6 будет реплицировать DFS-R.
> Выбирайте диск с запасом и с местом под теневые копии.

### Шаг 2. Указать путь порталу

В `C:\inetpub\ftp\appsettings.Production.json` добавьте секцию `Storage`
(не забудьте: правки в `appsettings.json` затираются при обновлении):

```json
{
  "ConnectionStrings": {
    "Portal": "Host=localhost;Port=5432;Database=portal;Username=portal_app;Password=..."
  },
  "Storage": {
    "RootPath": "D:\\PortalFiles"
  }
}
```

Обратные слэши в JSON удваиваются — это не опечатка.

### Шаг 3. Развернуть и создать структуру

```powershell
Stop-WebAppPool -Name "PortalPool"
cd C:\build\portal
git pull
dotnet publish src\Portal.Web -c Release -o C:\inetpub\ftp
Start-WebAppPool -Name "PortalPool"
```

Новые таблицы создадутся сами при запуске.

Дальше — в портале, под учётной записью администратора:

1. Раздел **Файлы** → создать папки верхнего уровня
   (их может создавать только администратор портала).
2. Для каждой открыть **Настройки и права доступа** и выдать права группам AD.

## Как устроены права

Три уровня, каждый включает предыдущий:

| Уровень | Что можно |
|---|---|
| **Чтение** | видеть папку, открывать её, скачивать файлы |
| **Запись** | дополнительно: загружать файлы, создавать подпапки, удалять СВОИ файлы |
| **Управление** | дополнительно: удалять любые файлы и саму папку, менять настройки и права |

Правила, которые стоит запомнить:

- **Права выдаются группам AD, не людям.** Отдельного списка пользователей
  портал не ведёт — управление остаётся в оснастке «Пользователи и компьютеры».
- **Права разных групп складываются.** Если человек состоит в двух группах
  с разными уровнями, действует наибольший.
- **Наследование включено по умолчанию.** Подпапка получает права
  родителя плюс свои. Выключается галочкой в настройках папки —
  тогда действуют только права самой папки. Так делают «закрытые» разделы
  внутри общего.
- **Администраторы портала (`WebAdmins`) попадают везде**, включая закрытые
  папки. Это осознанно: должен быть кто-то, кто может починить неудачно
  розданные права.
- **Папка видна, если доступно что-то внутри неё.** Иначе до разрешённой
  подпапки нельзя было бы добраться. При этом содержимое самой такой папки
  не показывается — только путь дальше.
- **Чужого не видно.** Папка без прав отвечает «не найдено», а не «доступ
  запрещён»: само существование папки «Приказы по кадрам» — уже сведения.

## Ограничения размера

Три уровня, от частного к общему:

1. **У папки** — поле «Предел размера одного файла». Пусто — берётся значение
   родительской папки.
2. **Общее по умолчанию** — `Storage:DefaultMaxFileSizeMb`, 50 МБ.
   Действует, если нигде выше не задано.
3. **Жёсткий предел** — `Storage:AbsoluteMaxFileSizeMb`, 200 МБ.
   Больше него папке выставить нельзя.

**Если поднимаете жёсткий предел, правьте ДВА места.** Кроме
`appsettings.json` есть ещё `web.config`:

```xml
<requestLimits maxAllowedContentLength="213909504" />
```

Это ограничение самого IIS, и оно срабатывает раньше приложения.
Держите его чуть больше, чем `AbsoluteMaxFileSizeMb` (запас на служебные
части запроса). Если забыть — крупный файл оборвётся с ошибкой 404.13,
и пользователь не увидит никакого понятного объяснения.

**Квота на папку** ограничивает суммарный объём. Пусто — без ограничения
(или как у родителя). В занятое место входят и файлы в корзине: они
по-прежнему лежат на диске.

## Автоочистка и корзина

**Автоочистка папки** по умолчанию **выключена**. Включается полем
«удалять файлы старше N дней» в настройках папки.

Важные особенности:

- очищенные файлы попадают **в корзину**, а не стираются сразу —
  у ошибки в настройке есть 30 дней на то, чтобы её заметили;
- срок **не распространяется на подпапки**: у каждой он свой.
  Так случайно назначенный на корень срок не выметет всё дерево;
- каждое такое удаление попадает в журнал действий.

**Корзина** хранит удалённое `Storage:TrashRetentionDays` дней (по умолчанию 30),
после чего файлы стираются с диска безвозвратно. В корзине человек видит
то, что удалил сам, плюс всё удалённое в папках, которыми управляет.

Фоновая уборка просыпается раз в `Storage:CleanupIntervalHours` часов
(по умолчанию 6). Общий выключатель — `Storage:CleanupEnabled`.

> Уборка работает внутри процесса сайта. Это нормально, пока веб-сервер один.
> Если появится второй, надо будет либо выключить её везде, кроме одного,
> либо вынести в отдельную службу.

## Запрещённые расширения

Загрузка `.exe`, `.bat`, `.ps1`, `.js`, `.lnk` и ещё примерно тридцати типов
отклоняется. Полный список — в `StorageOptions.BlockedExtensions`.

Смысл не в том, что портал «ловит вирусы» — он этого не умеет и не должен.
Смысл в том, чтобы хранилище внутри домена не стало удобной площадкой для
раздачи исполняемых файлов: ссылка на такой файл выглядит как ссылка
на доверенный внутренний ресурс, и открывают её без раздумий.

Проверяются все части имени, а не только последняя: `отчёт.exe.pdf`
тоже будет отклонён.

Изменить список можно в `appsettings.Production.json` — массив заменяется
целиком, перечисляйте все нужные значения:

```json
{ "Storage": { "BlockedExtensions": [ ".exe", ".bat", ".ps1" ] } }
```

## Журнал действий

Раздел **Журнал** в меню (только для администраторов) показывает,
кто что загружал, скачивал и удалял, с адресом и временем.
Есть фильтры по логину, действию и имени файла.

Записи о скачивании — вещь чувствительная сама по себе, поэтому журнал
закрыт для всех, кроме `WebAdmins`.

Журнал растёт: примерно по одной строке на каждое действие с файлом.
При 20 пользователях это тысячи строк в год — незаметно для PostgreSQL.
Если когда-нибудь понадобится, добавим автоматическую чистку старых записей.

## Как это лежит на диске

```
D:\PortalFiles\
    000001\
        3f8a2c1b9e4d4a7f8c2e1b5d6a9f0c3e
        7d1e4b8a2c9f4e6b8a1d3c5f7e9b0a2d
    000002\
        ...
```

Номер папки — её идентификатор в базе, имя файла — сгенерированный код.
Настоящие имена и расширения живут в базе данных.

Так сделано намеренно. Пользовательское имя никогда не попадает в путь
файловой системы, а значит невозможны выход за пределы хранилища через
`..\..\`, совпадение имён, запрещённые символы и слишком длинные пути.

**Обратная сторона: без базы содержимое диска нечитаемо.** Это осознанный
размен. Резервные копии базы и папки с файлами имеют смысл только вместе —
см. раздел ниже.

## Резервное копирование: теперь это критично

С появлением файлов список того, что нужно копировать, вырос:

| Что | Чем | Если потерять |
|---|---|---|
| База `portal` | `pg_dump` | пропадут объявления, структура папок, права и **имена всех файлов** |
| `D:\PortalFiles` | robocopy / штатное резервное копирование | пропадут сами документы |
| `C:\inetpub\ftp\App_Data\keys` | копирование файлов | все пользователи разом «разлогинятся» |
| `appsettings.Production.json` | копирование файлов | придётся вспоминать пароль базы и путь к хранилищу |

**База и папка с файлами копируются вместе и восстанавливаются вместе.**
По отдельности они бесполезны: на диске лежат файлы с обезличенными именами,
а в базе — имена без содержимого. Делайте обе копии в одно окно времени.

```powershell
$date = Get-Date -Format "yyyy-MM-dd"

& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" -U portal_app -d portal -F c `
    -f "E:\Backup\portal-$date.dump"

robocopy "D:\PortalFiles" "E:\Backup\PortalFiles-$date" /MIR /R:2 /W:5 /NP /LOG+:"E:\Backup\robocopy.log"
```

И проверьте восстановление хотя бы один раз. Копия, которую ни разу
не разворачивали, — это не копия, а предположение.

## Что предлагаю на будущее

Не сделано сейчас, чтобы не раздувать этап. Скажите, если что-то из этого
нужно раньше остальных.

**Поиск по имени файла.** Сейчас файл ищется глазами по папкам.
Поиск по всему хранилищу с учётом прав — работы немного, пользы много.

**Рекурсивное удаление папки.** Сейчас удалить можно только пустую.
Это сознательно, но если окажется неудобно — сделаем удаление
с подтверждением и подсчётом того, что будет уничтожено.

**Версии файлов.** Повторная загрузка файла с тем же именем сейчас создаёт
второй файл. Можно вместо этого хранить версии и давать откатиться.

**Ссылка на файл в объявлении.** Чтобы в объявлении можно было сослаться
на документ из хранилища, а не пересылать его почтой.

**Перемещение и переименование.** Сейчас файл нельзя перенести в другую
папку, а папку — переименовать. Не срочно, но однажды понадобится.

**Чистка журнала действий.** Пока он растёт без ограничений. При ваших
объёмах это не проблема на годы вперёд, но правило удаления записей старше
N лет когда-нибудь пригодится.
