# Проверка этапа 1

Сценарий приёмки. Проходить целиком после развёртывания — минут двадцать.
Отмечайте пункты; если какой-то не прошёл, в конце каждого раздела написано,
куда смотреть.

---

## А. Сайт поднялся

- [ ] `http://ftp.domen.pro/healthz` возвращает `ok`
- [ ] `http://ftp.domen.pro/` перенаправляет на `/Account/Login?returnUrl=%2F`
- [ ] Форма входа выглядит нормально: есть поля, кнопка, оформление применилось

По короткому имени, как будут заходить пользователи:

- [ ] `http://ftp/healthz` возвращает `ok`
- [ ] `http://ftp/` открывает ту же форму входа

Проверять обязательно с **клиентского компьютера**, а не с самого сервера:
короткое имя разворачивается в полное по списку DNS-суффиксов, а он на
сервере и на клиенте может отличаться.

Если оформления нет (голый текст) — не отдаётся `wwwroot/css/site.css`.
Проверьте, что папка `wwwroot` попала в `C:\inetpub\ftp`.

Если по короткому имени приходит ошибка «Invalid Hostname» или 404, а по
полному всё работает — не создана вторая привязка в IIS (шаг 5 инструкции
по развёртыванию). Если короткое имя вообще не разрешается — дело в DNS,
проверьте на клиенте `nslookup ftp`.

## Б. Вход работает

- [ ] Вход с правильным логином и паролем пользователя из `WebUsers` — попадаете на главную
- [ ] На главной видно ваше ФИО из AD (атрибут `displayName`)
- [ ] Видна почта из AD, если она заполнена
- [ ] В поле «Офис (по IP)» указан правильный офис
- [ ] В списке групп есть `WebUsers` и остальные ваши группы

Проверьте все три формата логина — все должны работать одинаково:

- [ ] `ivanov`
- [ ] `DOMEN\ivanov`
- [ ] `ivanov@domen.pro`

Если ФИО не подтянулось, а показан логин — в AD не заполнен `displayName`.
Это не ошибка портала.

## В. Отказы работают правильно

- [ ] Неверный пароль → «Неверный логин или пароль»
- [ ] Несуществующий логин → **то же самое сообщение**

Второе важно: разные сообщения превратили бы форму входа в способ выяснить,
какие учётные записи есть в домене.

- [ ] Пользователь с верным паролем, но **не** в `WebUsers` → «Пароль верный,
      но у вас нет доступа к порталу»
- [ ] После этого он остаётся на форме входа, на главную не попадает

Заведите для этой проверки временную учётку или временно уберите тестового
пользователя из `WebUsers`.

## Г. Защита от блокировки учёток

- [ ] Пять раз подряд ввести неверный пароль
- [ ] На шестой раз появляется «Слишком много неудачных попыток. Повторите через 5 мин.»
- [ ] **В оснастке AD учётная запись при этом НЕ заблокирована**

Последний пункт — главный. Именно ради него счётчик и сделан.

Проверить состояние учётки:

```powershell
Search-ADAccount -LockedOut | Select-Object Name, SamAccountName
```

Если учётка всё-таки заблокировалась — `Security:MaxFailedLoginAttempts`
в конфиге больше или равен порогу доменной политики. Уменьшите его.
Посмотреть доменный порог:

```powershell
Get-ADDefaultDomainPasswordPolicy | Select-Object LockoutThreshold, LockoutDuration
```

## Д. Разграничение прав

Под учётной записью **из `WebUsers`, но не из `WebAdmins`**:

- [ ] Пункта «Диагностика» в шапке нет
- [ ] Прямой переход на `http://ftp.domen.pro/Admin/Diagnostics` → страница «Доступ запрещён»

Под учётной записью **из `WebAdmins`**:

- [ ] Пункт «Диагностика» в шапке есть
- [ ] Страница открывается
- [ ] На ней правильно показан ваш IP
- [ ] Правильно определён офис
- [ ] Оба контроллера домена помечены «отвечает»

## Е. Выход и сессия

- [ ] Кнопка «Выйти» возвращает на форму входа
- [ ] После выхода переход на `http://ftp.domen.pro/` снова просит войти
- [ ] Кнопка «Назад» в браузере не возвращает в портал

Проверка cookie — откройте инструменты разработчика браузера (F12),
вкладка Application → Cookies:

- [ ] Есть cookie `Portal.Auth`
- [ ] У неё стоит флаг `HttpOnly`
- [ ] `SameSite` = `Lax`
- [ ] Флага `Secure` пока **нет** — так и должно быть, пока работаем по HTTP

## Ж. Проверка из второго офиса

С компьютера в подсети `192.168.112.0/20`:

- [ ] Вход работает
- [ ] На главной в поле «Офис (по IP)» указан **Офис 2**
- [ ] В поле «Проверено контроллером» указан `192.168.112.2`, а не `192.168.96.3`

Третий пункт подтверждает, что аутентификация не ходит через межофисный канал.

> Подсети офисов — `/20` (маска `255.255.240.0`), то есть офис 1 это
> `192.168.96.0`–`192.168.111.255`, а офис 2 — `192.168.112.0`–`192.168.127.255`.
> Проверять определение офиса стоит **не только** с адресов вида `192.168.96.x`
> и `192.168.112.x`: при неверно записанной маске такие адреса определяются
> правильно даже случайно. Возьмите компьютер из середины диапазона —
> например, `192.168.105.x` или `192.168.120.x`.

Проверка отказоустойчивости (по возможности, в нерабочее время):

- [ ] Заблокировать на межсетевом экране порт 389 к `192.168.112.2`
- [ ] Вход из второго офиса всё равно проходит — через контроллер первого офиса
- [ ] Занимает заметно дольше (до 10 секунд) — это ожидаемо, отрабатывает таймаут
- [ ] В журнале появилась запись «Контроллер домена ... недоступен, пробую следующий»

## З. Перезапуск не выкидывает пользователей

- [ ] Войти в портал
- [ ] `Restart-WebAppPool -Name "PortalPool"`
- [ ] Обновить страницу — вы всё ещё внутри

Если выкинуло — не работает сохранение ключей защиты данных.
Проверьте права на `C:\inetpub\ftp\App_Data` (шаг 6 инструкции по развёртыванию)
и что там появились файлы `key-*.xml`.

## И. Автотесты (необязательно)

На машине с установленными пакетами тестов:

```powershell
dotnet test
```

- [ ] Все тесты проходят (сейчас 25)

Они проверяют логику портала с заглушкой вместо AD: выдачу сессии,
разграничение по группам, выход, отказ формы без antiforgery-токена,
защиту от открытого редиректа. Живой домен для них не нужен.

Отдельно проверяются границы подсетей офисов — включая адреса из середины
диапазона `/20`, на которых как раз и всплывает ошибка в маске.

## Где смотреть журнал

Приложение пишет в стандартный вывод, а его подхватывает IIS —
если включён `stdoutLogEnabled` (см. раздел «Если что-то не работает»
в инструкции по развёртыванию).

Что искать по ключевым словам:

| Строка в журнале | Значит |
|---|---|
| `Пользователь ... вошёл с ...` | успешный вход |
| `Неудачный вход ...` | отказ, с причиной и IP |
| `Контроллер домена ... недоступен` | переход на запасной контроллер |
| `прошёл проверку пароля, но не состоит в группе` | человека нет в `WebUsers` |
| `Попытки входа для ... приостановлены` | сработал счётчик неудач |

Чтобы получить больше подробностей при разборе проблемы, поставьте
в `appsettings.json`:

```jsonc
"Logging": { "LogLevel": { "Portal.Web": "Debug" } }
```

и перезапустите пул.
