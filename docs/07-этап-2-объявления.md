# Этап 2: база данных и объявления

Что появилось:

- лента объявлений — читают все, у кого есть доступ к порталу;
- создание, редактирование и удаление — только группа `WebPublishers` и администраторы;

## Что нужно сделать на сервере

### Шаг 1. Установить PostgreSQL

Дистрибутив см. в [02-что-скачать.md](02-что-скачать.md).

При установке:

- **снимите галочку Stack Builder** — он полезет в интернет;
- задайте пароль пользователя `postgres` и запишите его в надёжное место;
- порт оставьте 5432;
- кодировку выберите **UTF8**;
- локаль подойдёт любая.

Проверка после установки:

```powershell
Get-Service postgresql*
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -c "select version();"
```

### Шаг 2. Создать базу и отдельного пользователя

Портал НЕ должен работать под учётной записью `postgres`: у неё права
суперпользователя, и ошибка в приложении в этом случае обойдётся дороже.
Заводим отдельного пользователя, который владеет только своей базой.

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres
```

Дальше в открывшейся консоли:

```sql
-- Придумайте длинный пароль и запишите его: он понадобится на шаге 3.
CREATE ROLE portal_app WITH LOGIN PASSWORD 'сюда-длинный-пароль';

CREATE DATABASE portal OWNER portal_app ENCODING 'UTF8';

-- Никому больше в этой базе делать нечего.
REVOKE ALL ON DATABASE portal FROM PUBLIC;

\q
```

Проверка подключения новым пользователем:

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U portal_app -d portal -c "select current_user;"
```

### Шаг 3. Дать порталу строку подключения

Строка подключения содержит пароль, поэтому её нет и не должно быть
в `appsettings.json`: этот файл лежит в репозитории.

**Способ, который рекомендую** — отдельный файл только на сервере.

Создайте `C:\inetpub\ftp\appsettings.Production.json`:

```json
{
  "ConnectionStrings": {
    "Portal": "Host=localhost;Port=5432;Database=portal;Username=portal_app;Password=сюда-длинный-пароль"
  }
}
```

Этот файл перекрывает `appsettings.json` и в репозиторий не попадает
(он указан в `.gitignore`). При обновлении портала командой `dotnet publish`
он не затирается.

Права на файл сузьте: пароль в нём лежит открытым текстом.

```powershell
$file = "C:\inetpub\ftp\appsettings.Production.json"

# убрать наследование прав от папки
icacls $file /inheritance:r

# оставить только администраторов, систему и пул приложений
icacls $file /grant "Администраторы:(R)" "SYSTEM:(R)" "IIS AppPool\PortalPool:(R)"
```

> Если группа называется `Administrators` (английская версия системы),
> подставьте это имя. Посмотреть текущие права: `icacls $file`

**Альтернатива** — переменная окружения в `web.config`:

```xml
<environmentVariables>
  <environmentVariable name="ASPNETCORE_ENVIRONMENT" value="Production" />
  <environmentVariable name="ConnectionStrings__Portal"
                       value="Host=localhost;Port=5432;Database=portal;Username=portal_app;Password=..." />
</environmentVariables>
```

Двойное подчёркивание — не опечатка: так в переменных окружения
записывается вложенность разделов конфигурации.

Разницы в безопасности почти нет — оба файла лежат рядом и читаются одними
и теми же людьми. Файл `appsettings.Production.json` удобнее тем, что
переживает `dotnet publish` без правок.

### Шаг 4. Создать группу публикаторов в AD

```powershell
New-ADGroup -Name "WebPublishers" -GroupScope Global -GroupCategory Security
```

Добавьте туда тех, кто будет писать объявления. Не забудьте, что они должны
состоять и в `WebUsers` — иначе на портал их просто не пустят.

Администраторы (`WebAdmins`) могут публиковать и без членства в `WebPublishers`.

Если имя группы другое, поправьте в `appsettings.json`:

```jsonc
"ActiveDirectory": {
  "PublisherGroup": "WebPublishers"
}
```

### Шаг 5. Развернуть новую версию

```powershell
Stop-WebAppPool -Name "PortalPool"

cd C:\build\portal
git pull
dotnet publish src\Portal.Web -c Release -o C:\inetpub\ftp

Start-WebAppPool -Name "PortalPool"
```

Таблицы в базе создадутся сами при первом запуске. Отдельный инструмент
для этого не нужен — так сделано специально, чтобы в сеть без интернета
не пришлось переносить ещё и `dotnet-ef`.

## Проверка

### А. База поднялась

- [ ] Войти администратором, открыть **Диагностика**
- [ ] «Состояние при запуске приложения» — «схема в порядке»
- [ ] «Отвечает сейчас» — «да»
- [ ] «Объявлений в базе» — 0

Таблица должна появиться в базе:

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U portal_app -d portal -c '\d "Announcements"'
```

### Б. Права на публикацию

Под учётной записью **из `WebUsers`, но не из `WebPublishers`**:

- [ ] Пункт «Объявления» в меню есть, лента открывается
- [ ] Кнопки «Написать объявление» НЕТ
- [ ] Прямой переход на `http://ftp/Announcements/Create` → «Доступ запрещён»

Под учётной записью **из `WebPublishers`**:

- [ ] Кнопка «Написать объявление» есть
- [ ] Объявление создаётся и появляется в ленте
- [ ] Под ним указаны ваше ФИО и время публикации

### В. Чужое править нельзя

Нужны две учётные записи из `WebPublishers` — назовём их А и Б.

- [ ] А публикует объявление
- [ ] Б открывает ленту: под объявлением А ссылок «Изменить» и «Удалить» НЕТ
- [ ] Б переходит по адресу `http://ftp/Announcements/Edit/1` напрямую → «Доступ запрещён»
- [ ] Администратор те же ссылки видит и может править

### Г. Текст объявления безопасен

- [ ] Опубликовать объявление с текстом:
      `<script>alert('привет')</script> и ссылка https://example.com`
- [ ] В ленте виден именно этот текст, никакого окна с сообщением не появляется
- [ ] Ссылка `https://example.com` стала кликабельной и открывается в новой вкладке
- [ ] Переносы строк в тексте сохранились

Это главная проверка этапа. Если бы разметка из текста выполнялась,
любой публикатор мог бы выполнить свой код в браузере у всех сотрудников.

### Д. Портал переживает падение базы

- [ ] `Stop-Service postgresql-x64-17`
- [ ] Вход в портал по-прежнему работает — он идёт через AD, а не через базу
- [ ] Раздел «Объявления» показывает «Объявления сейчас недоступны»
- [ ] На странице «Диагностика» видно «Отвечает сейчас — нет» с причиной
- [ ] `Start-Service postgresql-x64-17`
- [ ] Лента снова работает **без перезапуска пула**

Это сознательное поведение: раздел с объявлениями не должен ронять весь портал.

## Резервное копирование — теперь это важно

С этого этапа в портале появились данные, которые нельзя восстановить
пересборкой из исходников. Копировать нужно **три** вещи:

| Что | Чем | Если потерять |
|---|---|---|
| База `portal` | `pg_dump` | пропадут все объявления |
| `C:\inetpub\ftp\App_Data\keys` | обычным копированием файлов | все пользователи разом «разлогинятся» |
| `C:\inetpub\ftp\appsettings.Production.json` | обычным копированием | придётся заново вспоминать пароль базы |

Простейшая выгрузка базы:

```powershell
$date = Get-Date -Format "yyyy-MM-dd"
& "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" -U portal_app -d portal -F c `
    -f "D:\Backup\portal-$date.dump"
```

Поставьте это в планировщик заданий на ежедневный запуск и **проверьте
восстановление хотя бы один раз** — копия, которую ни разу не разворачивали,
это не копия, а предположение.

Восстановление:

```powershell
& "C:\Program Files\PostgreSQL\17\bin\pg_restore.exe" -U postgres -d portal --clean "D:\Backup\portal-2026-08-03.dump"
```

## Что осталось на потом

**Вложения в объявлениях.** Сознательно не делались: файлы появятся
на этапе 3, и вложения разумно строить поверх общего хранилища,
а не заводить для них отдельный механизм.

**Форматирование текста.** Сейчас объявления — обычный текст с автоматическим
распознаванием ссылок. Причина в [01-архитектура.md](01-архитектура.md)
и в комментариях к `PlainTextFormatter`: визуальный редактор означает приём
HTML от пользователя, а это отдельная библиотека очистки разметки и
постоянный риск XSS. Если жирный шрифт и списки всё же понадобятся,
правильный следующий шаг — Markdown, а не HTML-редактор.

**Уведомления о новых объявлениях.** Почтой или иначе — обсудим,
если понадобится.
